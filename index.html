Steps of AI Adoption

A Microsoft and GitHub capability map for moving from controlled access to intent-driven enterprise automation.

Important — not an official recommendationThis independent assessment is not an official Microsoft, GitHub or joint recommendation, endorsement or product roadmap. It is a proposed framework for enterprise discussion about AI-adoption maturity. Organizations must validate capabilities, availability, licensing and governance requirements against current official documentation.

Stages 0–1

Strong native coverage through Copilot governance, regional data controls, assisted development, reviews and GitHub security.

Stage 2

Credible for bounded fleets of coding agents, with repository, session-duration and review-capacity constraints.

Stage 3

Requires Microsoft Foundry, Agent Framework, Entra, Purview and Azure observability around GitHub.

Stage 4

Platform-enabling only. A 1,000-agent operating model remains a custom distributed system and organizational change.

Missing capabilities to close

These are the principal gaps between having capable products and operating a repeatable, evidence-driven enterprise AI governance system.

1

Unified AI application registry

No single Microsoft/GitHub inventory automatically combines approved models, Copilot surfaces, custom agents, MCP servers, owners, data classifications and business use cases.

2

Evidence collection and scoring

GitHub metrics, audit logs, Purview, Defender, Foundry evaluations and Azure configuration evidence must be normalized into a shared score and backed by source links.

3

Shadow AI discovery

Copilot governance does not discover every external AI application used by employees. Network, endpoint, identity and procurement signals are still needed.

4

Continuous recertification

Model, policy, residency, feature maturity and vendor terms change. Enterprises need expiry dates, material-change detection and automatic reassessment.

5

Score-to-policy enforcement

There is no turnkey control that converts a confidence score into GitHub rulesets, Entra access decisions, Purview DLP, Azure Policy or MCP restrictions.

6

Independent human assurance

Automated evidence extraction can be wrong. High-risk systems require accountable reviewers, recorded exceptions and separation between builders and approvers.

7

Cross-agent incident response

Enterprises need a common kill switch, containment process, forensic trail and recovery workflow spanning GitHub, Azure agents, models and connected tools.

8

Outcome and risk linkage

Usage analytics measure adoption, not business benefit or residual risk. Scorecards must connect activity to quality, security, productivity and customer outcomes.

0: Controlled access Governance gatekeeper Strong coverage 0

AI access is limited to approved users, models, repositories and use cases. Security, legal and procurement approvals dominate adoption.

Teams may experiment locally, but there is no trusted path for hosting, reviewing or operating agent-created artifacts.

Legacy approval processes, unclear data boundaries, licensing decisions and a focus on token cost rather than engineering outcomes.
  • GitHub Copilot Business and Enterprise policies
  • Seat, feature, model and MCP controls
  • Repository permissions and content exclusion
  • GitHub AI-credit budgets and audit logs
  • Copilot data residency for US and EU regions
  • Microsoft Entra ID and Conditional Access
  • Microsoft Purview, Azure Policy and Defender
  • Azure regional deployment, Private Link, VNet and encryption controls
  • Least-privilege repository access
  • Approved models and tools
  • Approved geographies and Azure Policy allowed-location rules
  • Enable the policy that restricts Copilot to data-residency-compliant models
  • Budget limits and audit streaming
  • Protected branches and Actions allowlists

Scope: GitHub documents in-region inference and associated data for generally available Copilot features when the separate residency policy is enabled. US and EU/EFTA are currently supported. Preview features, connected MCP services and unavailable regional models require separate review. Local prompts are also not fully visible in normal GitHub audit logs.
How to get from step 0 to 1: approve use cases, models and deployment geographies; document data flows and retention; establish least-privilege access; select pilot repositories; set cost limits and define human-review requirements.
1: AI-assisted development You + an agent Native ~1

One engineer works with one agent in the IDE, terminal or GitHub. Most changes are supervised and reviewed before merge.

Unlock: work that once filled an afternoon can be completed between meetings.

Human attention. Engineers inspect prompts, edits, tests and security findings because trust in self-verification is still limited.

Work remains mostly synchronous.
  • GitHub Copilot Chat and IDE agent mode
  • GitHub Copilot CLI
  • Copilot Spaces and custom instructions
  • Copilot code review
  • CodeQL, secret scanning and Copilot Autofix
  • Copilot usage metrics dashboard, REST API and NDJSON reports — GA
  • Auto model selection and task-aware routing
  • GitHub Copilot app sessions and canvases
  • Human PR approval and protected branches
  • Required tests, builds and code scanning
  • Custom instructions and scoped tools
  • Usage and cost monitoring

Gap: AI review cannot guarantee correctness or find every security issue. Spaces provide context, not orchestration.
How to get from step 1 to 2: encode standards in Copilot instructions and skills, add trusted test/build/security loops, use automatic review, and divide independent work into branch- and PR-sized tasks.
2: Parallel agent delivery Orchestrator Bounded coverage ~10

An engineer coordinates several coding tasks at once. Agents work on separate branches and PRs, validate their work, and return reviewable diffs.

Unlock: a maintenance backlog that took weeks becomes an afternoon of orchestration.

Review overload, overlapping edits, merge conflicts, task decomposition, context quality and AI-credit or Actions consumption.
  • Multiple Copilot cloud-agent sessions
  • Copilot CLI /fleet and subagents
  • Custom agents and agent skills
  • GitHub Issues, Projects and Actions
  • Copilot automations and scheduled workflows
  • Azure Boards to Copilot cloud-agent integration
  • Remote CLI steering on GitHub.com, GitHub Mobile, VS Code and JetBrains — GA
  • Cloud and local Copilot sandboxes — public preview
  • One task per branch and pull request
  • Required reviewers and status checks
  • Tool allowlists, hooks and firewall controls
  • Per-user budgets and security review

Gap: there is no published Copilot-agent concurrency SLA. Cloud-agent sessions are limited to one repository, one branch, one PR and 59 minutes.
How to get from step 2 to 3: introduce ownership and dependency graphs, durable queues, per-agent telemetry, structured review sampling and exception routing; move cross-repository orchestration into Microsoft Foundry or custom services.
3: Governed autonomous operations Manager of managers Integration-based ~100

Agent supervisors select specialized workers, route tasks and operate continuously. Humans review exceptions, outcomes and policy decisions rather than every edit.

Unlock: maintenance, cleanup and remediation become continuous background operations.

Trust, evaluation quality, identity lifecycle, rate limits, distributed state, downstream capacity, exception handling and cost.
  • Microsoft Foundry Agent Service
  • Microsoft Agent Framework orchestration
  • GitHub Copilot SDK and cloud sessions
  • Entra Agent ID and agent identities
  • Enterprise-managed OpenTelemetry export for VS Code and Copilot CLI
  • Application Insights and Foundry agent tracing
  • Purview, Defender and GitHub security controls
  • Per-agent identities and RBAC
  • Human approval for sensitive tools
  • Regional deployment, VNet isolation, DLP and audit
  • Evaluation, traces, alerts and cost telemetry

Gap: GitHub alone is insufficient. Durable orchestration, dependency handling, rollback and recovery require Microsoft services and custom engineering.
How to get from step 3 to 4: build a governed agent registry, hierarchical supervisors, durable state, continuous evaluation, circuit breakers, quota management, cost-aware model routing and explicit human authority for irreversible actions.
4: Intent-driven enterprise automation Executive steering by intent Custom architecture 1,000+

Large agent fleets are initiated by goals and events. Leaders set intent, policy and financial boundaries, then monitor outcomes and exceptions.

Unlock: quarter-long migrations and enterprise remediation programs become repeatable workflows.

Goal decomposition, systemic error propagation, quality drift, identity sprawl, economics, accountability and organizational redesign.
  • Custom agent fabric on Microsoft Foundry
  • Agent Framework supervisors and workflows
  • Azure queues, compute, storage and model routing
  • Entra, Purview, Monitor and Cost Management
  • GitHub as the code, PR and security system of record
  • M365 and Teams as human interaction channels
  • Hierarchical least privilege
  • Financial limits and anomaly detection
  • Formal SLOs and blast-radius controls
  • Independent assurance and staged autonomy

Gap: neither Microsoft nor GitHub offers a turnkey or capacity-guaranteed 1,000-agent system. This must be treated as a bespoke distributed system.
